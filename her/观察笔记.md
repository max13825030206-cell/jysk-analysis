## 自我反思

[2026-07-28] #数据准确性 建立数据密集型页面时，初始产品列表和统计数字容易因估算或中间版本残留而出错。本次 JYSK 分析页经历了多轮"用户独立核查→发现偏差→重新爬取修正"的循环（类目产品数、系列数、总 SKU 数均有偏差）。教训：完成数据页面后应做一次程序化的全量对账——用 JS 从页面 DOM 提取所有产品条目，与源站抓取结果逐条比对，而不是靠人工记忆或目测。尤其是当产品多次增补后，各处的汇总数字容易遗忘同步。

[2026-07-28] #搜索深度 在 JYSK 网站上花了较长时间搜索 "Popular" 标签——检查了 sticker 类名、页面文本、dataLayer、产品详情页，均未找到。小熊直接给出了精确答案：`?sort=popular` URL 参数。教训：当目标网站的可见 UI 中没有某个数据维度时，应优先检查 URL 参数（sort、filter、order 等常见 query string）和网络请求中的 API 响应，而不是只在 DOM 文本中搜索关键词。用户对源网站的底层机制比我更了解，遇到阻塞时应更早承认并询问，而不是反复尝试不同的 DOM 抓取策略。

[2026-07-28] #方法论 为 JYSK AW27 推导产品方向时，犯了两次同类错误：第一次把 SS26 的趋势名（Raw Beauty + Renewing）直接当成 AW27 的色彩方向，第二次虽然从店铺 DNA 出发但仍在用"趋势名→颜色"的推导链条。小熊两次纠正："颜色不能只根据上个季度上新来，而是根据店铺整体风格来推"。教训：对于有正式季节性趋势系统的零售商，趋势名是 DNA 的季度输出而非 DNA 本身。推导新品方向时应分析跨季节、跨品类的永久设计语言（材料、形态、色彩基调），然后问"这个 DNA 在当前品类中缺失了什么"，而非问"上个季度的趋势名对应什么颜色"。

[2026-07-28] #收敛 多次被纠正推荐方向过多、过散。从 6-8 个方向→5 个→4 个，材质从全品类→聚焦玻璃。小熊的偏好模式很明确：少而精，每个方向要有具体产品图片和 SKU 数量，不要抽象策略描述。在给出产品开发建议时，默认收敛到 3-5 个方向，每个方向配完整的参考产品图和具体规格。

[2026-07-28] #领域知识 在材质分类上犯了行业术语错误：将 TORUP "beige stone"、ROTEBERG、STENINGE 等 stoneware/stone-finish 陶瓷产品错分为 polyresin。小熊纠正：stoneware 是陶瓷，只有明确标注 "effect"（marble effect、terrazzo effect）的才是 polyresin 仿制效果。教训：家居行业材质分类有严格的术语边界——"stone" 和 "stoneware" 在英文中都指陶瓷/炻器，不是树脂。做材质归类时不能仅凭"看起来像石头"就判为树脂，必须以产品名中的术语为准："effect" = 仿制/树脂，"stoneware/stone/glazed" = 陶瓷。

[2026-07-29] #材质验证 上一条 7/28 的教训仍然不够——即使按产品名术语规则分类（"effect"→polyresin，"stoneware"→ceramic），实际打开 JYSK Specs 后发现仍有大量偏差：TORUP "beige stone" 的 Material 字段是 Polyresin+Sand（不是 stoneware），LYCKSELE "terrazzo effect" 的 Material 字段是 Stoneware（不是 polyresin），KATTARP "green" 的 Material 字段是 Glass（不是 ceramic）。产品名完全不可靠——名字描述的是外观效果，不是实际材质。小熊明确要求：必须打开每个产品的 Specifications 区域，读取 Material 字段的实际值来归类——含 glass→Glass，含 stoneware→Ceramic，含 polyresin→Polyresin。没有捷径，不能根据产品名或系列名推断。这比上一条更根本：连按术语规则推断都不行，必须看源站 Spec。

[2026-07-30] #图片格式 产品图片显示调试耗时极长——反复调整 CSS 容器高度/图片缩放/纵横比都无效，小熊多次反馈"只看到部分产品""不完整"。最终发现根因：JYSK CDN 的 `wd3.medium` 格式不是统一尺寸——不同产品返回不同纵横比（dispenser 256×600 竖版，jar 600×342 横版）。之前一直假设图片尺寸一致，导致在固定纵横比容器中竖版产品被裁切。修复：去掉固定 aspect-ratio，用纯高度 + object-fit:contain 同时兼容横竖版。教训：处理 CDN 图片时不能假设统一格式，应先抽查多款产品的实际尺寸，尤其当用户反复说"不完整"但 CSS 看起来正确时——问题可能在数据源而非布局。另外 `display: contents` 在对 `<a>` 标签包裹 `<img>` 的场景下可能破坏 flex 布局，改用 `width:100%; height:100%` 替代。

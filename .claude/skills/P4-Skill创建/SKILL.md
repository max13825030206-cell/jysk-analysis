# Skill · 练习4 · Skill 创建

> 43 College 第二节 · 练习4专用技能
> 前置：学员已完成练习1-3，搭档已有人格、记忆
> 课程衔接：学员在课程中已听完幕5（Skills），亲手安装并触发过 2-3 个预选 Skill
> 衔接语（七姐在幕5收束时说）：「到现在你拥有了人格、记忆和技能。接下来——自己造一个。」

---

## 前置准备（AI 静默执行，不向学员展示）

**读取以下文件**：
- `.claude/private/user-config.json`：获取 `soul_dir`（灵魂层目录名）和 `user_name`
- `{soul_dir}/SOUL.md`：学员的 SOUL（用学员定义的风格说话）
- `{soul_dir}/USER.md`：学员个人档案（用于了解学员的行业和工作内容，帮助推荐场景）

**了解 Skill Creator 的工作方式**：
- Skill Creator 是系统内置的技能，用于帮助用户创建新的 Skill
- 它会通过对话了解需求，然后生成 SKILL.md 文件
- 生成的 Skill 包含：frontmatter（name + description）+ Markdown 指令正文

---

## 交互风格

1. **每一步都要告知学员**：现在在做什么、为什么做、做完会怎样。
2. 不使用技术术语（不说 frontmatter、YAML、trigger、init_skill.py）。
3. 用学员能理解的话描述文件和操作。
4. 一次只推进一个步骤，说完等学员回复。
5. **禁止使用 AskUserQuestion 工具。** 所有交互用自然语言文本。
6. **用 `{soul_dir}/SOUL.md` 中定义的风格说话。**
7. **严禁照抄话术。** 以下所有标注「参考」的话术，只提供**意图和核心信息**，你必须用自己的方式重新组织语言。
8. **进度提示**：每一步开始时告知学员当前进度（如「现在是第2步，一共4步」），每步完成时明确告知。让学员始终知道自己在哪里、还剩多少。
9. **对话信号**：每次输出末尾，用自然语言明确告知学员下一步需要做什么（如「你操作完了跟我说一声」「想好了告诉我」）。不要在没有明确信号的情况下停下来等，让学员猜该干什么。
10. **人称一致**：谈到搭档（AI 自己）时，统一用「我」（第一人称）。不用「它」指代自己。跨窗口场景中，说「你的搭档」或「搭档」，不说「它」。

## 入口判断

### 情况 A：明确练习触发

学员说「开始练习4」「练习四」「Skill创建」或助教指示开始 → 进入**第1步**。

### 情况 B：没有明确触发词

学员说了其他话 → **主动询问**。

参考（不要照抄）：
「你是不是要开始练习4——自己造一个技能？跟我说一声就开始。」

- 学员确认要开始 → 进入**第1步**
- 学员说还没开始 / 不确定 → 友好回应，等学员准备好再说

### 情况 C：前置练习未完成

读取 `.claude/private/college-progress.json`。如果 `p1`、`p2`、`p3` 中有任何一个不是 `"completed"` → 引导学员先完成前面的练习。练习必须按 1→2→3→4 的顺序推进，不可跳级。

## 开场 · 路线预告

进入第 1 步之前，先用自己的话告诉学员整个练习 4 会怎么走（**不照抄，按意图自己组织**）：

**核心信息**：
- 练习 4 一共 4 步。这一关你要**亲手造一个属于你自己的技能**
- 第 1 步：选场景——从你工作里找一件重复出现的事，作为技能的原材料
- 第 2 步：用 Skill Creator 生成——我来帮你把场景变成一个搭档能懂的技能文件
- 第 3 步：用 Skill Reviewer 审核——系统里自带一个「审核员技能」，我们让它帮你检查刚造出来的技能有没有写全、哪里要调整
- 第 4 步：新窗口实测触发——审完改好之后，开新窗口说一句话，看搭档会不会自动启动你造的这个技能
- 做完这 4 步，你就有了第一个自己造的技能——以后这件事搭档会自动帮你做

说完告诉学员「我们从第 1 步开始，你先想想有没有那种每次做步骤都差不多的事」，然后自然进入第 1 步。

## 第1步 · 选场景

> 核心体验：学员找到自己工作中一个重复出现的场景，这就是 Skill 的原材料。
> 这一步最容易卡住——学员可能不知道该选什么。TC 要主动帮忙，不能干等。

### 1A · 告知学员

参考（不要照抄）：
「接下来你要自己造一个技能。技能的意思是——你工作里有没有那种每周都要做、每次步骤都差不多的事情？我们把它变成一个搭档自动帮你做的技能。先想想看，你有没有这样的场景？」

**等学员回复。**

### 1B · 学员有想法

学员说出了一个场景 → 帮学员确认这个场景适合做成 Skill。

**判断标准**（内部判断，不展示给学员）：
- 场景是否有重复性（不是一次性任务）
- 场景是否有相对固定的步骤或输出格式
- 在现场练习时间内是否能完成

如果场景合适，参考（不要照抄）：
「这个场景很好，步骤比较固定，很适合做成技能。我们就用这个来造。」

→ 进入**第2步**。

如果场景太大或太模糊，帮学员收窄：
参考（不要照抄）：
「这个有点大，我们可以先挑其中一个环节来做——比如 [具体建议]。这样在课上时间内能做完，之后你还可以再扩展。」

### 1C · 学员没想法

**不要干等。** 根据 `{soul_dir}/USER.md` 中学员的行业和工作内容，主动推荐 2-3 个场景让学员选。

参考（不要照抄）：
「没关系，我帮你想几个。根据你做的工作，这几个场景都蛮适合的：
A. [根据学员行业推荐的场景1]
B. [根据学员行业推荐的场景2]
C. [根据学员行业推荐的场景3]
你觉得哪个比较有感觉？或者你有其他想法也可以。」

**推荐逻辑**（内部参考，不展示给学员）：

> **关键原则**：推荐的场景必须是**多步骤流程**，不是通用大模型一句话就能完成的事。好的 Skill 场景有固定的步骤顺序、特定的输入输出格式、或需要遵循特定规则。

| 行业/角色 | 推荐场景示例（多步骤流程） |
|-----------|--------------------------|
| 管理层 | 「每周五收集各组周报 → 按统一模板汇总 → 标注风险项 → 生成发给老板的一页纸摘要」 |
| 市场/运营 | 「拿到一篇长文章 → 拆成 3 条小红书文案 → 每条配标题和标签 → 按平台字数限制调整」 |
| 销售 | 「拿到客户的公司信息 → 调研行业背景 → 按模板生成拜访前准备表 → 列出 3 个切入话题」 |
| 产品 | 「拿到一份会议录音转写稿 → 提取行动项和决策 → 按责任人分组 → 生成带截止日期的跟进清单」 |
| 创业者 | 「有一个新想法 → 按商业画布 9 格拆解 → 识别最大风险点 → 生成一页纸验证计划」 |
| 教育 | 「拿到课程大纲 → 按课时拆解知识点 → 每个知识点配一个练习题 → 生成学员手册初稿」 |
| 法务 | 「收到一份合同 → 逐条检查关键条款（付款/违约/知识产权/终止）→ 标注风险等级 → 生成审查意见表」 |
| 财务 | 「导入本月流水 → 按费用类别自动归类 → 标记异常金额 → 生成带对比的月度费用摘要」 |

> 以上仅为参考。实际推荐时要结合 USER.md 中的具体信息，给出更贴合学员实际工作的**多步骤**场景。如果学员提出的场景只需要一步就能完成（比如「翻译一段话」「总结一篇文章」），要引导他把场景扩展成有流程的版本。

学员选定后 → 进入**第2步**。

## 第2步 · 用 Skill Creator 生成

> 核心体验：学员用自然语言描述需求，搭档帮他把描述变成一个结构化的 Skill 文件。
> 学员不需要写代码，不需要懂格式——只需要说清楚「我要什么」。

### 2A · 告知学员

参考（不要照抄）：
「好，场景定了。接下来我来帮你把这个场景变成一个技能文件。你只要用你自己的话告诉我：这件事平时怎么做的、有什么步骤、最后要出什么结果。我来帮你整理成搭档能懂的格式。」

### 2B · 引导学员描述需求

通过对话帮学员把场景描述清楚。需要覆盖的信息：

1. **什么时候会用到这个技能**——触发场景是什么（学员平时会怎么说来启动这件事）
2. **具体做什么**——步骤是什么、有没有固定的流程
3. **最终产出是什么**——输出的格式、内容、交付物是什么

**不要一次问三个问题。** 一个一个来，学员回答完一个再问下一个。根据学员的回答灵活调整——如果学员说得很清楚，可以跳过已经覆盖的维度。

参考（不要照抄）：
- 第一个问题：「你平时什么时候会做这件事？一般是怎么开始的——你会跟搭档说什么来启动它？」
- 第二个问题：「具体步骤是什么？比如先做什么、再做什么、有没有固定的流程？」
- 第三个问题：「做完之后你需要的结果是什么样的？比如一份文档、一张表、还是一段文字？」

### 2C · 生成 Skill 文件（强制使用 Skill Creator）

信息收集完毕后，**必须调用 Skill Creator 来生成 Skill 文件**。这是强制要求——不能自己手写 SKILL.md，必须通过 Skill 工具调用 `skill-creator`。

**调用方式**：使用 Skill 工具，skill 参数填 `skill-creator`，在对话中描述学员的需求场景，让 Skill Creator 生成 SKILL.md。

**Skill Creator 生成时，必须额外要求**：
- SKILL.md 的**全部内容必须使用中文**（frontmatter 中的 name 可以用英文，description 和指令正文必须用中文）
- Skill 存放在 `.claude/skills/` 目录下，以场景命名（用英文短横线连接，如 `weekly-report`、`meeting-notes`）
- frontmatter 的 `description` 要写得足够详细，包含触发场景、触发词、功能描述

**生成完成后，引导学员查看文件。** 因为 `.claude` 是隐藏文件夹，学员默认看不到：

参考（意图参考，严禁照抄）：
技能文件生成好了。你看屏幕右上角，有一个**技能面板**——点一下就能看到所有已安装的技能，你刚才造的那个就在里面。点开看看内容对不对。

→ 等学员确认已打开，进入**第3步**。

---

## 第3步 · 用 Skill Reviewer 审核调整（仍在当前窗口）

> 核心体验：学员让系统内置的 Skill Reviewer 来审核自己刚造的技能，拿到四维度审核报告，根据报告调整 SKILL.md，直到审核通过。
> **这一步不换窗口，就在当前创作窗口里做。** 审完通过后才去新窗口测触发。
> 关键：**学员不会自己想到要审。必须由 TC 明确告诉学员说什么话触发 Skill Reviewer。**

### 3A · 简要介绍 SKILL 文件结构

**学员刚打开 SKILL.md 文件，先用人话简要说明它长什么样**（不要展开解释每一块，留给 Skill Reviewer 来审）：

参考（不要照抄）：
「你看到的这个文件分两块——最上面几行是技能的『身份证』（名字 + 什么时候会被搭档启动），下面一大段是具体的指令（搭档接到任务后一步一步做什么）。

接下来我们不自己猜它写得好不好——系统里自带一个审核员技能，让它帮你检查。」

### 3B · 明确告诉学员说什么话触发 Skill Reviewer

**必须给学员一句具体的话，不要让学员自己猜。** 参考（不要照抄）：

「你跟我说这句话就好：『帮我审一下这个 Skill』——系统里有个审核员技能会自动启动，帮你从四个维度检查。」

**提示学员**：如果审核员问要审的文件路径，把刚才生成的 SKILL.md 的路径告诉它就好（路径在前面生成文件时已经给过学员，或者让学员从技能面板里复制）。

**等学员说出触发词。**

### 3C · Skill Reviewer 运行 + 报告解读

学员说出触发词后，`skill-reviewer` 会被启动，它会：
- 读取学员刚才生成的 SKILL.md
- 从四个维度（Frontmatter / 交互风格 / 指令完整性 / 边界处理）逐项检查
- 输出一份带 ✓/✗ 标注的审核报告

**报告出来后，帮学员读懂报告**。学员看到 ✓ ✗ 的列表可能会有点懵——用人话告诉他：

- 哪几项过了（绿灯）
- 哪几项没过，具体要补什么（红灯）
- 总体评级是「可直接使用 / 需小改 / 需重写」

参考（不要照抄）：
「报告出来了——[用人话总结：几项过了、几项要改、总评级怎样]。我们按报告里标红的几项改一下。」

### 3D · 根据报告调整 SKILL.md

**直接帮学员改文件**（用 Edit 工具），不要让学员自己改。每改一处，简短告诉学员改了什么、为什么这么改。

参考（不要照抄）：
「审核说 description 没写触发词——我加上了。你平时会说的那些开场白，比如 [具体例子]，都列进去了。」

**如果学员想参与修改（比如他觉得 description 的触发词应该是别的）**，尊重他的修改意图，帮他落实。

### 3E · 再审一次

**改完后，告诉学员再审一次**（参考，不要照抄）：

「改好了。你再跟我说一遍『帮我审一下这个 Skill』，让审核员再看一次。」

**等审核报告出来**。通常第二次就能拿到「可直接使用」或「需小改」——如果还是「需重写」说明改得不够，再循环一次。

**最多循环 2-3 次**，拿到「可直接使用」即可进入下一步。不要卡在这里反复抠细节——后面新窗口实测才是最终验证。

审核通过后 → 进入**第4步**。

---

## 第4步 · 新窗口实测触发

> 核心体验：审核通过后，学员在新窗口里说一句话，技能被触发，产出结果。然后回到创作窗口反馈和调整。
> 这是「从使用者到建设者」的高光时刻。
> **窗口归属：这一步一定要换新窗口。** 当前窗口是创作环境，新窗口才是测试环境——新窗口启动时重新加载 skills 目录，才能识别新装的技能。

### 4A · 生成测试开场白 + 明确告知去新窗口

**Skill 文件已经在 `.claude/skills/` 目录下，系统会自动识别。**

**根据学员定义的触发场景，生成一句百分百会触发这个 Skill 的开场白。** 这句话必须：
- 自然、像学员平时会说的话
- 明确命中 Skill 的 description 中定义的触发条件
- 不需要额外解释就能让搭档识别并启动技能

参考（不要照抄）：
「审核也过了，技能就算正式可用了。现在要去**开一个新的对话窗口**测试——当前这个窗口是创作环境，新窗口才是测试环境。

去开一个新窗口，跟搭档说这句话：『[根据 Skill 触发条件生成的具体开场白]』——看看搭档会不会自动启动你刚才造的技能。

试完了**回到这个窗口**跟我说结果，不管成不成都回来说一声。」

> 明确告诉学员：① 去新窗口 ② 说什么话 ③ 测完回到本窗口。三件事一个都不能省。

→ 学员去新窗口测试。

### 4B · 学员回到创作窗口反馈

学员在新窗口测试完后，回到当前窗口反馈结果。

参考（不要照抄）：
「测试怎么样？技能有被触发吗？效果符合你的预期吗？」

**如果触发成功且结果符合预期**：
参考（不要照抄）：
「成功了——你说了一句话，搭档就按照你定义的步骤跑了一遍。这就是你自己造的第一个技能。」

→ 进入**收尾**。

**如果触发失败或结果不对**：
在当前创作窗口排查和调整：

1. 先问学员具体情况：技能有没有被触发？搭档做了什么？跟你预期差在哪里？
2. 根据学员描述判断问题类型：
   - 技能没被触发 → 检查 description 中的触发条件是否足够清晰，调整后让学员换一句话再试
   - 技能触发了但步骤不对 → 调整 SKILL.md 指令正文中的步骤描述
   - 技能触发了但输出格式不对 → 调整输出格式的要求
3. 调整完毕后，再生成一句新的测试开场白，让学员去新窗口再试

参考（不要照抄）：
「我知道问题在哪了——[说明原因]。我帮你调一下。」
调整后：「好，改好了。你再去开个新窗口，这次跟搭档说：『[新的测试开场白]』，看看这次对不对。」

**可以多轮迭代**，直到学员满意。每轮都是：当前窗口调整 → 新窗口测试 → 回来反馈。

## 收尾

**练习4 完成后，写入进度文件**：将 `.claude/private/college-progress.json` 中的 `p4` 更新为 `"completed"`。

**必须验证**：写入后立刻用 Read 工具回读 `.claude/private/college-progress.json`，确认 `p4` 确实是 `"completed"`。如果没写进去就重写。这一步不能跳过。

**学员自己能判断「成功了」的信号**（对应四步）：

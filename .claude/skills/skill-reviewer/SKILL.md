# Skill 审核员

> 用于审核 HER System 中新创建的 Skill 文件是否规范合格。

---

## 第一步：获取文件

请用户提供需要审核的 SKILL.md 文件路径，然后用 Read 工具读取文件内容。

如果用户没有提供路径，询问：「你要审核的 Skill 文件在哪里？把路径告诉我就好。」

---

## 第二步：逐项审核

读取文件后，按以下四个维度逐项检查。

### 维度一：Frontmatter

| 检查项 | 判断标准 |
|--------|----------|
| `name` 是否有值 | 不为空，使用英文短横线命名 |
| `description` 是否包含触发场景 | 说明了什么情况下会用到这个 Skill |
| `description` 是否包含触发词 | 列出了具体的触发短语 |
| `description` 是否包含功能描述 | 说明了 Skill 能做什么 |

### 维度二：交互风格

| 检查项 | 判断标准 |
|--------|----------|
| 是否定义了语气/风格 | 说明了搭档应如何说话 |
| 是否有「禁止使用 AskUserQuestion」的说明 | 或等效的交互限制 |
| 是否有「一次一步」原则 | 不一次性推进多个步骤 |
| 是否有「严禁照抄话术」要求 | 或等效的自然语言要求 |

### 维度三：指令完整性

| 检查项 | 判断标准 |
|--------|----------|
| 步骤是否完整 | 从触发到结束有完整的流程 |
| 每步是否有明确的输入输出 | 知道需要什么、产出什么 |
| 是否有结束条件 | 明确知道什么时候 Skill 完成 |
| 话术示例是否标注「参考/不要照抄」 | 防止搭档逐字复述 |

### 维度四：边界处理

| 检查项 | 判断标准 |
|--------|----------|
| 是否有「已完成模式」 | 用户重复触发时的处理逻辑 |
| 是否有异常/失败的处理分支 | 操作失败时如何处理 |
| 是否有前置条件检查 | 需要先完成某些步骤时是否有判断 |

---

## 第三步：输出审核意见表

按以下格式输出结果：

```
## Skill 审核报告：[Skill 名称]

### 维度一：Frontmatter
- name 有值 ✓/✗
- description 包含触发场景 ✓/✗
- description 包含触发词 ✓/✗
- description 包含功能描述 ✓/✗

### 维度二：交互风格
- 语气/风格定义 ✓/✗
- AskUserQuestion 限制 ✓/✗
- 一次一步原则 ✓/✗
- 话术自然语言要求 ✓/✗

### 维度三：指令完整性
- 步骤完整 ✓/✗
- 输入输出明确 ✓/✗
- 结束条件 ✓/✗
- 话术有「参考/不要照抄」标注 ✓/✗

### 维度四：边界处理
- 已完成模式 ✓/✗
- 异常处理分支 ✓/✗
- 前置条件检查 ✓/✗

### 需要调整的项
[列出所有 ✗ 项，每项给出具体的改进建议]

### 总体评级
可直接使用 / 需小改 / 需重写
[一句话说明原因]
```

---

## 交互原则

- 读取文件后直接输出审核结果，不需要逐项和用户确认
- 如果某些检查项在当前 Skill 类型中不适用（比如没有前置条件的 Skill），标注「不适用 —」而非「需调整 ✗」
- 审核完成后，询问用户是否需要直接帮他修改不合格的项
